판단이 아니라, 근거를 남긴다

Evidence, not assumptions — FabricIQ · WorkIQ · WebIQ · FoundryIQ

FabricIQ, WorkIQ, WebIQ, FoundryIQ 네 개의 서로 다른 근거 원천을 분리해서 수집하고, Azure AI Foundry에서 결합·평가해 하나의 응답으로 만드는 과정을 다룹니다. 참가자는 각 근거의 책임과 한계를 sourceTrace로 설명하고, 일부 소스가 실패해도 과도한 추론 없이 부분응답 또는 차단으로 대응하는 법을 익힙니다.

운영 시간 480분 · 09:00–17:00
트랙 구성 FabricIQ → WorkIQ → WebIQ → FoundryIQ
최종 결과 sourceTrace 분리된 Microsoft IQ 응답

네 가지 근거 원천

FabricIQ 내부 정형 지표 WorkIQ M365 내부 근거 WebIQ 공개 웹 citation FoundryIQ 권위 지식·결합
01
왜 넷으로 나누는가

최종 답변은 네 칸으로 읽습니다

숫자, 맥락, 최신성, 결론을 한 모델이 한 번에 만들면 근거를 검증할 수 없습니다. Microsoft IQ는 이 네 가지를 서로 다른 책임을 가진 원천으로 쪼갠 뒤, 마지막에만 결합합니다.

1

내부 수치

FabricIQ가 Lakehouse와 Ontology로 계산·검증한 정형 지표.

2

내부에서 확인된 이유

WorkIQ가 ACL을 지킨 채 찾아낸 Outlook·Teams·SharePoint·OneDrive 근거.

3

외부의 최신 상황

WebIQ가 수집한 공개 웹 citation과 관찰 시각·적용 범위·한계.

4

권위 지식과 결론

FoundryIQ의 권위 지식과 Foundry Agent Service의 결합·경고·조치 제안.

예시 — 질문을 네 조각으로 나누기

04
데이터 모델과 핵심 질의

14개 엔터티 · 20개 관계 · SQL로 검증하는 질문

Track1은 14종 원천 테이블을 마스터·이벤트·브릿지 엔터티로 재정의하고, 20개 관계로 연결합니다. 물리 FK를 넘는 다중 홉 논리 관계까지 정의해야 “캠페인이 반품까지 어떻게 이어졌는가” 같은 경로형 질문에 답할 수 있습니다.

마스터 엔터티 (5)

Customer Product Channel Campaign Promotion

이벤트 엔터티 (7)

Order OrderItem Payment Shipment Return SupportTicket InventorySnapshot

브릿지 엔터티 (2)

OrderPromotion CampaignAttribution

관계 예시 — 물리 FK와 논리(다중 홉) 관계

관계(동사형)카디널리티구현 근거
Customer places Order1 : Norders.customer_id
Order has Payment1 : Npayments.order_id — 재시도 결제가 있어 1:1로 고정하지 않음
Order fulfilled_by Shipment1 : Nshipments.order_id
Campaign drives CampaignAttribution1 : N브릿지 테이블로 Order·Customer를 함께 참조
Promotion influences Order (logical)N : Morder_promotions + orders — 직접 FK 아님
Customer purchases Product (logical, multi-hop)N : Morders → order_items — 2단 홉 경로

Q1 예시 — 결제 실패가 캠페인 전환율에 미치는 영향

분석 경로 Campaign → CampaignAttribution → Order → Payment. 승인 결제(SUCCESS, RETRYSUCCESS, AUTHORIZED) 기준으로 전환율을 계산해, 마케팅 문제와 결제 운영 문제를 분리합니다.

WITH campaign_orders AS ( SELECT ca.campaign_id, ca.order_id FROM campaign_attribution ca ), payment_flags AS ( SELECT p.order_id, MAX(CASE WHEN payment_status = 'FAILED' THEN 1 ELSE 0 END) AS has_failed, MAX(CASE WHEN payment_status IN ('SUCCESS','RETRYSUCCESS','AUTHORIZED') THEN 1 ELSE 0 END) AS has_authorized FROM payments p GROUP BY p.order_id ) SELECT co.campaign_id, COUNT(*) AS attributed_orders, AVG(COALESCE(pf.has_failed, 0)) AS payment_failure_rate, AVG(COALESCE(pf.has_authorized, 0)) AS conversion_rate FROM campaign_orders co LEFT JOIN payment_flags pf ON co.order_id = pf.order_id GROUP BY co.campaign_id ORDER BY conversion_rate ASC;
지표값(근사 · seed 20260701)
귀속 캠페인 수약 60개
캠페인당 귀속 주문약 30–40건
결제 실패율 하위 그룹 → 전환율0.65–0.71 → 0.29–0.35
결제 실패율 상위 그룹 → 전환율0.13–0.17 → 0.83–0.87
failure_rate ↔ conversion_rate 상관약 −1.0

전환율 하위 캠페인은 마케팅 품질이 아니라 결제 실패가 병목임을 수치로 보여줍니다 — FoundryIQ가 세 근거를 결합할 때 참조하는 것이 바로 이런 FabricIQ 계산 결과입니다.

최소 권한, 검증된 최소 신뢰

  • 실제 임직원 데이터가 아닌 샘플·격리 테넌트만 사용합니다.
  • 고객명, 이메일, 주문번호, 내부 URL, 미공개 지표, 문서 전문, 토큰을 웹 검색어에 넣지 않습니다.
  • 웹 페이지의 지시문은 명령이 아니라 신뢰도를 평가할 데이터로 취급합니다.
  • 검색 결과가 제안하는 URL, 파일 또는 외부 작업을 자동 실행하지 않습니다.
  • 최소 권한을 적용하고 WorkIQ 결과가 M365 ACL을 준수하는지 별도 계정으로 확인합니다.
  • 시크릿이나 토큰 예시는 문서·구성·로그·스크린샷에 남기지 않습니다.

운영 준비 확인

  • WebIQ 검증기가 Q1~Q3, citation 6개에 대해 PASS
  • Track2 고정 검색어 5개 중 4개 이상 검색 성공
  • Track2 품질 항목 8개 중 6개 이상이 75점 이상
  • normal Q1~Q3와 fallback 5종의 strict 평가가 failed: 0
  • normal 응답의 sourceTrace에 네 IQ가 모두 분리되어 표시
  • simulation 응답과 브리핑에 fixture 안내가 표시
  • 공개 웹만 남은 상태가 blocked
  • live 운영 시 실제 URL citation, M365 ACL, adapter와 Responses API를 별도 승인 환경에서 검증
