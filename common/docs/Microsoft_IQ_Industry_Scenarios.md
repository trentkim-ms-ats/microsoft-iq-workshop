# Microsoft IQ 산업별 대표 활용 시나리오

> 대상: Microsoft IQ 워크숍 참가자
> 용도: 산업별 적용 방식을 토의하고, 조직별 PoC 또는 운영 설계의 출발점으로 쓰는 재사용형 시나리오 템플릿

이 문서는 여섯 산업의 대표 활용 사례를 Microsoft IQ의 역할 경계에 맞춰
구체화합니다. 실제 회사, 개인, 환자, 고객, 미공개 KPI 수치 또는 현재 외부 사건을
예시로 사용하지 않습니다. 각 조직은 자체 정책, 데이터 정의, 권한 모델, 승인 체계에
맞게 범위와 임계값을 정해야 합니다.

이 문서는 기존 유통/이커머스 공통 질문 Q1-Q5, Track1-4 런타임, fixture, 평가
계약을 대체하거나 확장하지 않습니다. 공통 워크숍 구조는
[Microsoft IQ 워크숍 통합 계획](Microsoft_IQ_Workshop_Integrated_Plan.md)을
따릅니다.

## 1. 공통 실행 원칙

모든 시나리오는 다음 순서로 진행합니다.

~~~text
Track1 FabricIQ
  → Track2 WorkIQ
  → Track3 WebIQ
  → Track4 FoundryIQ
  → 사람 승인 후 운영 조치
~~~

| 구성 요소 | 담당 범위 | 이 문서에서 하지 않는 일 |
| --- | --- | --- |
| FabricIQ | 내부 정형 지표 계산, 기준선 비교, Ontology 관계 경로 검증 | 메일·회의록·웹 페이지에서 수치 역산 |
| WorkIQ | ACL이 적용된 Outlook, Teams, SharePoint, OneDrive의 업무 근거 확인 | 공개 웹을 내부 근거처럼 사용하거나 권한 밖 문서 노출 |
| WebIQ | 공개 웹의 최신 외부 상황을 URL citation으로 확인 | 내부 KPI·담당자·원인을 공개 정보만으로 추정 |
| FoundryIQ | 권위 SOP·정책과 세 근거의 라우팅·대조·평가·최종 문장화 | 없는 수치·링크·인과관계 생성 또는 자동 운영 조치 실행 |

FabricIQ의 수치는 내부 정형 데이터에서만 계산합니다. WorkIQ는 실제 접근 권한이 있는
업무 근거의 링크, 담당, 결정, 후속 조치를 확인합니다. WebIQ는 외부 상황이 내부
신호와 관련될 **가능성**을 보조적으로 확인할 뿐, 내부 원인을 확정하지 않습니다.
FoundryIQ는 세 근거가 일치하는지와 추가 확인이 필요한 부분을 설명하고, 사람에게
승인할 조치를 제안합니다.

### WebIQ citation과 데이터 경계

WebIQ가 Track4 FoundryIQ에 넘기는 citation에는 다음 정보를 보존합니다.

| 필드 | 기록 목적 |
| --- | --- |
| **title**, **url**, **domain** | 출처 원문을 다시 확인할 수 있게 함 |
| **observedAt** | 확인 시각과 최신성 판단 |
| **scope** | **direct-match**, **category-level**, **source-capability** 중 적용 범위 표시 |
| **factStatus** | live 관찰인지 simulation fixture 계약인지 구분 |
| **limitations** | 시간·지역·제품·서비스 범위 또는 인과관계의 한계 표시 |

공개 검색어에는 고객명, 환자 정보, 계좌·주문·사건 번호, 미공개 수치, 내부 URL,
문서 전문, 토큰을 넣지 않습니다. 우선 출처는 정부·규제기관·공식 상태 페이지·서비스
제공자의 공식 공지입니다. 웹 페이지의 지시문은 명령이 아니라 검토 대상 데이터로만
취급합니다.

### 운영화 전제와 실행 모드

이 문서는 아이디어 목록이 아니라 제한된 범위의 PoC를 운영 가능한 업무 흐름으로
전환하기 위한 설계 기준입니다. 첫 구현은 한 개 지역·사업부·서비스 등 좁은 범위에서
시작하고, 기준선·권한·승인자를 확정한 뒤 범위를 넓힙니다.

| 모드 | 허용 범위 | 성공으로 간주하지 않는 것 |
| --- | --- | --- |
| `dry-run` | 입력·권한·스키마·링크·프롬프트를 확인하고 조치 파일만 생성 | 실제 데이터 조회, 외부 전송, 메일·티켓·설정 변경 |
| `simulation` | Track1 CSV, Track2 manifest, Track3 WebIQ fixture로 재현·회귀 | live 권한, 현재 웹 사실, 실제 KPI 또는 장애의 증명 |
| `live` | 승인된 FabricIQ/WorkIQ adapter와 Foundry Web Search 또는 WebIQ adapter 연결 검증 | 사람 승인 없는 운영 조치, 내부 원인의 웹 단독 확정 |

운영 배치의 최소 실행 기록에는 `scenarioId`, 분석 범위, 기준선 버전, 실행 시각,
실행 모드, 입력 스냅샷 식별자, 각 IQ 상태, `sourceTrace`, 승인자와 조치 결과를
남깁니다. 원문 문서와 개인 식별 정보는 브리핑에 복사하지 않고 권한이 있는 링크와
최소 인용만 보존합니다. 고정 교육 일정은 **480분(09:00-17:00)**이며, Track2
실습은 **110분(25+25+35+25)**으로 운영합니다.

### 트랙 인계 패키지와 검수 게이트

패키지는 사람이 읽을 수 있는 Markdown 요약과 기계 검증 가능한 JSON을 함께
제공합니다. 값이 없으면 빈 문자열로 성공을 표시하지 말고 `status`, `reason`,
`limitations`에 명시합니다.

```text
Track1 FabricIQ
  -> TRACK2_WORKIQ_HANDOFF_PACKAGE
Track2 WorkIQ
  -> TRACK3_WEBIQ_HANDOFF_PACKAGE
Track3 WebIQ
  -> TRACK4_FOUNDRYIQ_HANDOFF_PACKAGE
Track4 FoundryIQ
  -> 승인 대기 브리핑 + 평가 결과 + 감사 로그
```

| 인계 | 최소 필드 | 검수 기준 |
| --- | --- | --- |
| FabricIQ → WorkIQ | `scenarioId`, 분석 단위·기간·지역, KPI·기준선, 엔터티·관계 경로, `semanticKeys`, 데이터 최신 시각, 제한 | 핵심 경로 3개와 KPI 계산이 CSV/쿼리로 재현되고 단위가 명시됨 |
| WorkIQ → WebIQ | ACL 확인 상태, 검색 범위·필터, 내부 근거 링크 5개 이상, 근거별 `owner`, `decision`, `nextAction`, 재현 질의 3개, 누락 문서 | 8개 품질 항목 중 6개 이상 PASS(75점 이상), 권한 밖 링크 0건 |
| WebIQ → FoundryIQ | `title`, `url`, `domain`, `observedAt`, `scope`, `factStatus`, `limitations`, 검색어 privacy 점검, 관련성 판단 | Q1~Q3 각 citation 2개 이상, 공식 출처 우선, 내부 식별자 0건 |
| FoundryIQ → 승인자 | 근거별 요약, 불일치, confidence가 아닌 근거 상태, 제안 조치, 영향 범위, 담당자, 만료 시각, 승인·거부·보류 선택지 | `sourceTrace`에 FabricIQ·WorkIQ·WebIQ·FoundryIQ가 모두 표시되고 자동 실행 없음 |

각 adapter의 요청은 다음 공통 키를 사용합니다.

```json
{
  "scenarioId": "MFG-01",
  "question": "불량률 변화와 함께 확인해야 할 원인 후보는 무엇인가?",
  "semanticKeys": ["ProductId", "WorkOrderId", "EquipmentId", "InspectionDate"]
}
```

FabricIQ는 `structuredMetrics`, `highlights`, `sourceTrace`, WorkIQ는 ACL 적용
`evidenceLinks`, `sourceCoverage`, 필요 시 `sourceTrace`, WebIQ는 `webCitations`
목록을 반환합니다. 인증·ACL·schema·HTTP 오류는 명시적 실패로 기록합니다.
FoundryIQ 재시도는 일시적 429/5xx에 한해 **5초→10초→20초, 최대 3회 재시도
(초기 호출 포함 총 4회 시도)**로 고정합니다. 재시도 후에도 실패하면 해당
근거를 partial 또는 blocked로 전환하고 원인을 브리핑에 표시합니다.

### 운영 승인, 안전장치, 평가

각 시나리오에는 업무 책임자(결정권자), 데이터 소유자, 개인정보·보안 검토자,
서비스 운영자를 시작 전에 지정합니다. 제안 조치는 `proposed` 상태로만 생성하고,
승인자·승인 시각·정책 버전·실행 결과가 없는 조치는 완료로 집계하지 않습니다.
다음 조치는 항상 사람 승인을 요구합니다.

- 제조: lot 격리, 출하 보류, CAPA 개시·종결
- 물류·리테일: 재배차, 가격·프로모션 변경, 보상·대량 안내
- 금융: 계좌 제한, 거래 차단, 법정 신고·제출
- 헬스케어: 환자별 진단·트리아지·처방·치료 결정
- 통신: 네트워크 설정 변경, 현장 출동, 대외 장애 공지

PoC의 최소 평가 세트는 정상 질문 3개와 FabricIQ 실패, WorkIQ 실패, WebIQ 실패,
내부 근거 동시 실패, 전체 실패를 포함합니다. 평가는 숫자 정확성, 근거 링크
유효성·권한, 외부 citation 범위, 미확인 가설의 표시, 승인 경계, 재현성을 별도로
채점합니다. FabricIQ 또는 WorkIQ 실패는 해당 근거가 없는 `partial`, WebIQ만
실패하면 `외부 최신 근거 없음`을 포함한 `partial`, 두 내부 근거가 모두 실패하면
웹 근거가 남아도 `blocked`입니다.

### 시나리오를 실제 업무로 전환하는 6단계

1. **범위 고정:** 분석 단위, 기간, 지역, 제외 대상, 데이터 최신성 SLA를 문서화합니다.
2. **기준선 승인:** 정상 기간·비교군·분모·임계값을 데이터 소유자와 승인합니다.
3. **관계 경로 검증:** Ontology 경로를 샘플 레코드로 추적하고 중복·누락을 기록합니다.
4. **근거 패키지 구성:** WorkIQ는 ACL·문서 버전·담당자를, WebIQ는 citation 범위와
   관찰 시각을 보존합니다.
5. **승인형 브리핑 시범:** 최소 2주(또는 조직이 정한 충분한 정상·이상 구간) 동안
   제안만 생성하고 false positive, 누락, 승인 소요 시간을 측정합니다.
6. **운영 전환 심사:** 정확성·재현성·권한·감사 로그·비용·롤백 절차를 확인한 뒤
   제한된 사용자에게만 live를 허용합니다.

### 표준 브리핑과 fallback

각 시나리오의 FoundryIQ 브리핑은 다음 순서로 읽습니다.

1. **핵심요약** — 탐지된 내부 신호와 현재 판단 상태
2. **수치근거** — FabricIQ가 계산한 지표와 비교 기준
3. **문서근거** — WorkIQ가 확인한 ACL 적용 내부 문서·대화·승인
4. **외부근거** — WebIQ citation의 사실 범위와 한계
5. **조치안** — SOP·정책에 비춰 사람이 검토·승인할 다음 조치
6. **주의사항** — 미확인 가설, 누락 근거, 개인정보·운영 제한

최종 응답의 **sourceTrace**에는 **FabricIQ**, **WorkIQ**, **WebIQ**,
**FoundryIQ**를 각각 명시합니다.

| 상태 | FoundryIQ 처리 |
| --- | --- |
| FabricIQ, WorkIQ, WebIQ 모두 사용 가능 | 근거를 분리해 결합하고 승인 대상 조치를 제안 |
| FabricIQ 또는 WorkIQ 중 하나 실패 | 누락 근거와 재확인 필요성을 명시한 **partial** 응답 |
| WebIQ만 실패 | **외부 최신 근거 없음**을 명시한 **partial** 응답 |
| FabricIQ와 WorkIQ가 모두 실패 | 공개 웹만으로 내부 원인을 분석하지 않고 **blocked** 처리 |

**simulation**의 WebIQ fixture는 현재 웹 사실이나 실제 운영 호출 결과가 아닙니다.
실제 운영에서는 권한, 데이터 보호, 연결 승인, 정책 검토를 마친 환경에서만
**live** 검증을 수행합니다.

## 2. 시나리오 카드 읽는 방법

각 카드는 아래 질문에 답하도록 구성합니다.

| 항목 | 참가자가 설계할 내용 |
| --- | --- |
| 업무 배경·범위 | 누가, 어떤 기간·지역·조직·상품 또는 서비스 범위에서 결정을 내려야 하는가 |
| 탐지 신호·질문 | 어떤 이상 신호가 발생했고, 무엇을 확인해야 하는가 |
| FabricIQ | 데이터 도메인, 핵심 KPI, 비교 기준, Ontology 관계 경로 |
| WorkIQ | ACL 적용 검색 대상, 확인할 결정·담당·예외·진행 상황 |
| WebIQ | 민감정보 없는 공개 확인 질문, 우선 출처, 관련성 한계 |
| FoundryIQ | 대조할 SOP·정책, 결론 표현 방식, 승인 전 제안할 조치 |
| 완료 기준 | 근거 분리, 미확인 항목, 사람 승인 지점이 브리핑에 드러나는가 |

아래 Ontology 경로는 설계 예시입니다. 실제 구현에서는 조직의 데이터 모델과
의미 정의에 맞게 엔터티·관계·키를 검증한 뒤 사용합니다.

## 3. MFG-01 — 제조: 품질 이상 조기 감지 및 원인 후보 검증

### 업무 배경·범위

품질 책임자와 생산 책임자는 특정 제품군, 생산라인, 교대, 작업지시, 공정 단계,
설비, 원자재 lot, 분석 기간을 정합니다. 목표는 불량 신호가 기준선에서 벗어났을 때
원인을 단정하지 않고, 생산·설비·자재·검사 관점의 원인 후보를 검증하는 것입니다.

### 탐지 신호와 핵심 질문

- 불량률, first-pass yield, 재작업률 또는 결함 코드 분포가 조직의 기준선에서
  의미 있게 벗어났는가?
- 같은 기간의 공정·설비·교대·원자재 lot 변화가 신호와 시간적으로 겹치는가?
- 작업 SOP 또는 검사 기준의 편차를 뒷받침하는 내부 근거가 있는가?
- 출하 보류, 추가 검사, CAPA 개시가 필요한 수준인가?

### FabricIQ — 정형 신호

| 설계 요소 | 내용 |
| --- | --- |
| 주요 데이터 | 제품, 작업지시, 생산실적, 공정 단계, 검사 결과, 결함 코드, 설비 상태·정지, 보전 이력, 원자재 lot, 공급사 |
| 핵심 KPI | 불량률, first-pass yield, 재작업률, 결함 코드별 비중, 설비 정지·경보 패턴 |
| 비교 기준 | 제품군·라인·교대·공정별 기준선과 이전 정상 기간 또는 유사 작업지시 |
| 예시 관계 경로 | **Product → WorkOrder → ProcessStep → Equipment → Inspection**, **MaterialLot → Supplier**, **WorkOrder → Shift** |

ACL이 적용된 교대 인수인계, 품질 huddle 회의록, CAPA 기록, 작업지침과 개정 이력,
공정 변경 승인, 설비 보전 기록, 공급사 품질 협의 문서를 검색합니다. 다음 사항을

### WebIQ — 공개 확인

시간, 제품 범주, 공급 범위가 일치하지 않으면 외부 근거는 원인 후보가 아니라

**추가 확인이 필요한 편차**, **정책과 일치하는 조치**, **근거 불충분**으로 표현합니다.

  승인을 요청할 것인가?

### FabricIQ — 정형 신호

| 설계 요소 | 내용 |
| --- | --- |
| 주요 데이터 | 권역, 사이트·셀, 네트워크 요소, 성능 지표, 경보, 계획 변경, 작업지시, 집계 서비스·고객 영향 |
| 핵심 KPI | 가용성, 트래픽·혼잡, 지연, 패킷 손실, handover·통화절단, alarm burst, 집계 영향 규모 |
| 비교 기준 | 지역·서비스·요소별 기준선, 변경 전후 창, 정상 시간대 |
| 예시 관계 경로 | **Region → Site/Cell → NetworkElement → PerformanceMetric/Alarm**, **PlannedChange → WorkOrder → ServiceImpact** |

### WorkIQ — 내부 업무 맥락

NOC bridge 기록, 변경·유지보수 승인, 현장 출동 보고, runbook, 장애 커뮤니케이션
초안·승인 기록을 확인합니다. WorkIQ 근거로 현재 완화 조치, 담당 팀, 금지된 변경,
복구 절차를 검증합니다.

### WebIQ — 공개 확인

공식 기상·재난·전력·규제 공지와 승인된 대형 행사 공지를 확인합니다. 경쟁사의
공개 상태 페이지는 시장 맥락일 수 있지만, 자사 장애의 원인 증거가 아닙니다.
시간·지역·서비스 범위가 맞지 않는 외부 정보는 가설로도 과장하지 않습니다.

### FoundryIQ — 정책 대조와 승인 조치

FoundryIQ는 runbook, 영향 등급 정책, 변경관리 정책, 장애 커뮤니케이션 절차와
근거를 대조해 검증 순서, 현장 출동 후보, 고객 안내 초안을 제안합니다. 네트워크
설정 변경, 현장 출동, 대외 공지는 NOC 또는 권한 있는 책임자의 승인 없이는
실행하지 않습니다.

### 완료 기준

성능 신호, 내부 변경·복구 맥락, 외부 환경의 제한, 영향 등급과 승인 지점이
명확히 구분되면 완료입니다.

## 8. RTL-01 — 리테일: 수요 변화 조기 감지 및 매장·상품 대응 최적화

### 업무 배경·범위

MD, 매장 운영, 공급·재고 책임자는 SKU 또는 상품군, 매장·채널, 지역, 프로모션,
가격, 재고, 분석 기간을 정합니다. 목표는 수요 변화의 신호를 조기에 확인하고,
매장·상품 대응의 우선순위를 사람에게 제안하는 것입니다.

### 탐지 신호와 핵심 질문

- 매출·수요 예측 편차, sell-through, 재고 가용성·품절, 마진, 취소·반품·문의,
  채널 전환 중 어떤 신호가 기준선에서 벗어났는가?
- 가격·프로모션·진열·보충·공급 제약 또는 지역별 수요 변화와 시점이 겹치는가?
- 어떤 SKU·매장·채널을 우선 확인하고, 배분·보충·프로모션·안내 중 무엇을
  승인 대상 조치로 제안할 것인가?

### FabricIQ — 정형 신호

| 설계 요소 | 내용 |
| --- | --- |
| 주요 데이터 | SKU·상품군, 매장·채널, 재고, 판매 주문, 가격, 프로모션, 반품, 취소, 집계 고객 문의 |
| 핵심 KPI | 수요 예측 편차, sell-through, 재고 가용성·품절, 마진 지표, 취소·반품·문의, 채널 전환 |
| 비교 기준 | 상품·매장·채널·지역·프로모션별 기준선과 유사 기간 |
| 예시 관계 경로 | **Product/SKU → Store/Channel → Inventory → SalesOrder → Promotion/Price → Return/SupportCase** |

### WorkIQ — 내부 업무 맥락

점장 일일 보고, MD 협업, 프로모션 캘린더, 가격·마진 승인, 공급·보충 이슈,
반품 분석, 매장 운영 공지를 확인합니다. WorkIQ는 현장 관찰, 이미 승인된 계획,
실행 중인 조치와 담당자를 확인하며, 문서만으로 매출·마진 수치를 계산하지 않습니다.

### WebIQ — 공개 확인

공개 경쟁사 가격·재고는 이용 약관과 관찰 시각을 지키며 확인하고, 공식 트렌드,
기상, 지역 행사 정보를 보조 근거로 수집합니다. 외부 동향은 내부 수요 변화의
확정 원인이 아니며, 상품·지역·기간 범위가 맞을 때만 관련 가능성을 설명합니다.

### FoundryIQ — 정책 대조와 승인 조치

FoundryIQ는 가격·마진 가드레일, 재고 배분·보충 정책, 프로모션 승인 기준,
고객 안내 정책과 세 근거를 대조합니다. 배분, 보충, 진열, 프로모션, 가격 변경,
발주 또는 고객 안내는 책임자의 승인 후에만 실행하도록 제안합니다.

### 완료 기준

수요 신호와 비교 기준, 현장·MD 근거, 공개 맥락의 한계, 가격·마진·재고 정책,
사람 승인 조치가 분리된 브리핑으로 제공되면 완료입니다.

### 공통 데이터 품질과 재현성 체크

- **최신성:** 각 KPI와 문서의 마지막 갱신 시각을 기록하고, SLA를 넘긴 입력은
  `stale`로 표시해 정상 결과와 섞지 않습니다.
- **분모와 표본:** 비율의 분모, 제외 규칙, 최소 표본 수, 시간대·시간 지연을
  함께 저장합니다. 표본이 부족하면 `insufficient-evidence`로 제안만 합니다.
- **중복·조인:** 주문·작업지시·케이스·이벤트의 식별자와 중복 제거 규칙을
  기록하고, Ontology 경로에서 many-to-many 증폭이 없는지 샘플로 확인합니다.
- **문서 버전:** WorkIQ 링크에는 문서 버전·작성/갱신 시각·권한 확인 결과를
  남기며, 삭제·권한 변경 시 이전 브리핑의 접근 정책도 재검토합니다.
- **외부 근거 만료:** WebIQ citation의 `observedAt`와 만료 기준을 저장하고,
  기간·지역·서비스 범위가 달라지면 관련성 판단을 다시 수행합니다.
- **재현성:** 동일한 입력 스냅샷과 버전(`pipeline`, `prompt`, `model`,
  `toolset`)으로 다시 실행해 핵심 수치·상태·근거 목록이 일치하는지 확인합니다.

### 장애·예외 대응 runbook

| 징후 | 즉시 조치 | 재개 조건 |
| --- | --- | --- |
| FabricIQ adapter timeout/schema 오류 | 마지막 정상 결과를 최신 결과처럼 사용하지 않고 `정형 수치 미검증` 표시, 입력·스키마 버전 확인 | 헬스체크와 동일 질문 재실행이 성공하고 수치 재현 |
| WorkIQ ACL/검색 오류 | 문서 링크를 추측하거나 권한 밖 결과를 우회하지 않음, 검색 범위·권한 요청 기록 | ACL 점검 PASS와 샘플 링크의 실제 접근 확인 |
| WebIQ citation 부족·범위 불일치 | 외부 원인 문장을 제거하고 `외부 최신 근거 없음` 또는 제한 표시 | 공식 출처 2건 이상과 범위·관찰 시각 검수 |

| 기준선 변경·정책 버전 충돌 | 해당 실행을 보류하고 이전 버전과 변경 diff를 검토 | 데이터 소유자·정책 소유자 승인 및 버전 고정 |
