01 / Concept

Ontology는 업무의 공통 언어입니다

분리된 테이블을 업무 개념과 관계로 설명하고, 그 정의를 원천 데이터에 연결합니다.

ENTITY TYPE

무엇인가?

Customer · Order · Product
업무에서 중요한 객체의 유형을 정의합니다.

PROPERTY

어떤 특징이 있나?

customer_id · product_name
엔터티를 식별하고 설명하는 속성입니다.

RELATIONSHIP

어떻게 연결되나?

Customer places Order
객체 사이의 업무상 관계를 이름으로 표현합니다.

엔터티 유형은 설계도이고, 실제 데이터의 각 고객·주문·상품은 그 유형에 대응하는 인스턴스입니다.
02 / Architecture

데이터 위에 의미 계층을 얹습니다

업무 질문“어떤 고객이 어떤 상품을 구매했는가?”
Ontology 정의Customer · Order · OrderItem · Product와 이들 사이의 관계
데이터 바인딩엔터티 속성과 관계 키를 원천 테이블·컬럼에 매핑
원천 데이터Lakehouse의 customers · orders · order_items · products
데이터를 모두 Ontology로 복사하는 것이 아닙니다. Ontology는 정의와 바인딩을 제공하며, 실제 질의는 소비 경험과 원천의 실행 경로가 담당합니다.
03 / Comparison

Foreign Key와 같은 연결, 다른 목적

DATABASE

Foreign Key

orders.customer_id가 customers.customer_id를 참조한다는 데이터 구조상의 제약입니다.

DB에서 제약을 실제로 적용하면 없는 고객을 참조하는 주문을 차단할 수 있습니다.

ONTOLOGY

Customer places Order

동일한 연결에 “고객이 주문을 생성한다”는 이름과 업무 맥락을 부여합니다.

관계 자체가 DB의 FK 제약을 생성하거나 참조 무결성을 강제하지는 않습니다.

PK/FK처럼 보이는 컬럼이 존재하는 것과 DB에 실제 제약이 활성화된 것은 다릅니다. 단순한 모델에서는 둘의 구조가 상당히 유사할 수 있습니다.

InlineBase64는 API 전송 인코딩이며 암호화나 별도의 의미 모델이 아닙니다.

05 / Standards

THIS LAB

Fabric 정의

Fabric 스키마의 JSON 정의와 바인딩으로 업무 개념을 원천 데이터에 연결합니다.

JSON 관계 정의만으로 OWL 추론이나 SPARQL 지원이 자동 보장되지는 않습니다. 공개 정의 형식만으로 서비스 내부 저장 방식도 단정할 수 없습니다.
06 / Multi-hop

단순한 질문 뒤에는 여러 홉이 있습니다

“어떤 고객이 어떤 상품을 구매했는가?”라는 업무 질문을 실제 테이블 경로로 펼칩니다.

Customer고객
→
Order고객이 생성한 주문
→
OrderItem주문에 포함된 상품 행
→
Product주문 항목이 참조한 상품
경로연결 컬럼관계명
Customer → Ordercustomer_idCustomer places Order
Order → OrderItemorder_idOrder includes OrderItem
OrderItem → Productproduct_idOrderItem references Product

화살표는 이해를 위한 탐색 방향입니다. 원천 관계의 실제 선언 방향은 계약을 확인합니다.

07 / Cardinality

Customer ↔ Product는 N:M입니다

BUSINESS VIEW

Customer purchases Product

한 고객은 여러 상품을, 한 상품은 여러 고객이 구매할 수 있습니다. 같은 고객의 반복 구매도 가능합니다.

DATA VIEW · 가상의 예

중간 주문이 연결을 설명

C01 → O01 → P01
          → P02

C02 → O02 → P01
고객–상품 쌍만 남기면 주문 시점·수량·반복 구매 이력이 사라집니다. 실제 분석에서는 Order와 OrderItem을 유지해 집계 단위를 정합니다.
08 / Lab contract

논리 관계는 계약에 선언됩니다

logical_relationships:
  - name: Customer_purchases_Product
    display_name: "Customer purchases Product (logical)"
    from_entity: Customer
    to_entity: Product
    cardinality: "N:M"
    derived_via: "orders + order_items"
WHAT IT SAYS

업무 의미와 근거 경로

  • from_entity / to_entity: 시작과 끝
  • cardinality: N:M이라는 설계상 설명
  • derived_via: 근거가 되는 중간 테이블 설명

ontology_contract.yaml 열기 ↗

관계 계약은 업무 의미를 설명합니다. 실행 가능한 질의 계획을 선언한 것은 아닙니다.

09 / Implementation boundary

관계 선언 ≠ 자동 JOIN

생성하는 것

논리 관계 타입

생성기는 Customer와 Product 사이의 관계 정의를 만들고 derived_via를 설명 문자열에 반영합니다.

이 랩에서 생성하지 않는 것

실행 가능한 다중 홉 연결

이 논리 관계를 위한 Contextualization이나 실행 가능한 JOIN은 생성하지 않습니다. 관계 인스턴스가 자동 생성·탐색된다고 보장할 수 없습니다.

실제 연결은 원천 테이블 질의 또는 해당 환경에서 지원되는 실행 경로로 검증합니다. 이는 이 랩 생성기의 범위이며, 모든 Fabric 버전의 기능 한계를 뜻하지 않습니다.
10 / Verification

실제 연결은 원천 데이터로 확인합니다

SELECT DISTINCT
    c.customer_id, p.product_id, p.product_name
FROM customers AS c
JOIN orders AS o
    ON o.customer_id = c.customer_id
JOIN order_items AS oi
    ON oi.order_id = o.order_id
JOIN products AS p
    ON p.product_id = oi.product_id;
INTERPRETATION

이 쿼리가 보여 주는 것

  • 주문에 포함된 고객–상품 쌍을 확인합니다.
  • DISTINCT는 반복 주문을 하나의 쌍으로 합칩니다.
  • 주문별 이력과 수량은 별도 집계 단위가 필요합니다.
  • “구매 완료”라면 결제·취소·반품 기준을 추가로 정의해야 합니다.

예시 SQL은 논리 경로 검증용이며 완결된 구매 판정 규칙이 아닙니다.
