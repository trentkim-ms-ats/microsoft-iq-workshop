01 / Business question

질문 하나를 서로 다른 증거로 나눕니다

“배송 지연은 반품률과 고객 불만 티켓에 어떤 영향을 미치는가?”

FABRICIQ

수치

배송·반품·티켓 관계와 지표를 정형 데이터로 계산

WORKIQ

내부 맥락

권한이 허용된 문서와 업무 대화에서 관련 논의 확인

WEBIQ

외부 사실

공개 웹에서 확인 가능한 외부 정보와 출처 확보

FOUNDRYIQ

통합 판단

출처·시각·한계와 경고를 유지해 브리핑 구성

상관관계와 업무 문서의 진술은 인과관계 증명이 아닙니다. 외부 웹만으로 내부 원인을 단정하지 않습니다.
스피커 노트

같은 질문에도 지표, 내부 문서, 외부 확인의 출처가 다릅니다. 각 소스가 대답할 수 있는 범위를 먼저 나누세요.

02 / Architecture

연결은 책임과 계약으로 이뤄집니다

FabricIQLakehouse · Ontology → 내부 정형 지표
WorkIQM365 샘플 테넌트 → 권한이 적용된 내부 문서 근거
WebIQ공개 웹 → URL · 관찰 시각 · 범위가 있는 citation
Foundry IQ권위 지식 · 정책 · 재사용 지식 기반
Agent Service도구 라우팅 · 근거 결합 · 평가 · fallback → 최종 브리핑
이 다이어그램은 책임과 흐름입니다. 제품 간 자동 연결이나 현재 라이브 구성 완료를 의미하지 않습니다.
스피커 노트

Foundry IQ의 권위 지식과 Foundry Agent Service의 도구 오케스트레이션을 구분합니다. 각 소스의 권한 및 실행 모드는 독립적으로 확인합니다.

03 / Operational boundary

시연 결과의 출처와 모드를 밝힙니다

DRY-RUN

계획만 확인

예정된 작업을 보여줄 뿐 M365 배포·메일 배송을 증명하지 않습니다.

SIMULATION

재현 가능한 fixture

Track1 CSV, Track2 manifest, Track3 fixture로 결합과 실패 정책을 확인합니다.

LIVE

승인된 실제 호출

샘플 환경의 adapter, 권한, Web Search, Foundry 모델을 별도 승인 후 검증합니다.

저장소에 완성된 라이브 FabricIQ/WorkIQ adapter 서버는 없습니다. 미구성 시 개별 클라우드 화면과 simulation을 분리해 시연합니다.
스피커 노트

로컬 manifest는 실시간 WorkIQ 검색이나 ACL 증명이 아닙니다. fixture는 현재 웹의 실제 장애·경보·리콜을 증명하지 않습니다.

04 / Track 1 · FabricIQ

정형 데이터에 업무 의미를 연결

CSV 14종주문·배송·반품 등
→
Lakehouse테이블로 준비
→
Ontology엔터티·관계·바인딩
→
SQL 검증정형 경로와 기준값

화면에서 보여줄 것

Lakehouse 테이블 → Ontology 모델 → 질문의 SQL 결과 → Track2 인계 패키지

초보자를 위한 설명

Ontology는 테이블을 대체하지 않고 무엇이 무엇과 어떤 관계인지 설명합니다. FK 제약을 자동 강제하지 않습니다.

스피커 노트

Track1의 P1 데이터 품질 사례는 개념과 영향만 설명합니다. 탐지·수정이나 별도의 게이트로 바꾸지 않습니다. Track1 데모 상세

05 / Track 1 · multi-hop

“고객이 상품을 구매했다”의 실제 경로

Customer고객
→
Order주문
→
OrderItem주문 상품
→
Product상품

업무 관점: N:M

한 고객은 여러 상품을, 한 상품은 여러 고객이 구매할 수 있습니다. 중간 주문은 시점·수량과 반복 구매를 보존합니다.

랩의 구현 경계

Customer_purchases_Product는 논리 관계 타입입니다. derived_via는 설명이며 자동 JOIN이나 관계 인스턴스를 만들지 않습니다.

스피커 노트

다중 홉 경로는 실제 테이블에 대한 별도 SQL 등으로 검증합니다. 주문에 포함된 상품이라는 사실과 결제 완료·반품 여부는 구분하세요.

보여줄 것

08 / Track 4 · FoundryIQ

근거를 합쳐도 출처는 분리합니다

INPUT

질문 + 네 책임

정형 지표, 내부 문서, 외부 citation, 권위 지식을 구분합니다.

ORCHESTRATE

라우팅 + 검증

adapter 응답 및 출처 상태를 확인하고 필요한 경우 경고합니다.

OUTPUT

응답 + trace

근거 링크, citation, 한계, 조치와 IQ별 sourceTrace를 확인합니다.

라이브 adapter는 scenarioId, question, semanticKeys를 받는 workshop POST JSON 계약입니다. 원시 제품 URL이 아닙니다.
스피커 노트

먼저 Q2 응답과 tool_a_metrics.json을 함께 보여줍니다. Q1·Q2의 Track1 SQL과 simulation은 산식 또는 모집단이 다르므로 같은 baseline으로 단정하지 않습니다. simulation 브리핑은 사람이 지표·경고·citation 한계를 보완해야 하는 초안이며 실제 모델 호출이 아닙니다. Track4 데모 상세

09 / Failure policy

실패했을 때도 정직하게 답합니다

WEB DOWN

부분응답

내부 근거는 유지하고 외부 최신 근거 없음을 표시합니다.

WORK DOWN

부분응답

업무 문서 근거 없음을 표시하고 공개 웹으로 내부 근거를 대체하지 않습니다.

INTERNAL DOWN

분석 차단

FabricIQ와 WorkIQ가 모두 실패하면 웹 결과가 있어도 blocked입니다.

재시도: 5초 → 10초 → 20초, 최대 3회 재시도 = 최초 호출 포함 최대 4회 시도. Fabric 단독 실패와 전체 실패도 별도로 시연합니다.
스피커 노트

normal Q1~Q3와 fabric-down, work-down, web-down, internal-down, all-down의 평가 결과를 확인합니다. simulation 실패 주입은 실제 장애가 아닙니다.

10 / Demo handoff

각 트랙의 산출물이 다음 화면으로

Track1 → 2Ontology 식별·모델·매핑·제한·검색 키·경로
Track2 → 3내부 근거 5건 이상 · 재현 질의 3개 · 품질 6/8 이상
Track3 → 4Q1~Q3 각각 citation 2개 · 출처 품질 5/6 이상 · 개인정보 점검
Track4 → 결과IQ별 sourceTrace · 정상 및 fallback 평가 · 브리핑
Track1 → Track2 → Track3 → Track4 순서를 지키며, 각 인계가 실제 관찰인지 fixture인지 함께 기록합니다.
스피커 노트

인계 패키지는 다음 트랙이 무엇을 신뢰하고 무엇을 제한으로 알아야 하는지 전달합니다. 성공 표시만으로 실측 근거를 대체하지 않습니다.

11 / Cloud readiness

클라우드 데모는 준비와 승인이 먼저

사전 구성

  • Fabric workspace·Lakehouse·Ontology 및 샘플 CSV
  • 격리 M365 테넌트·검색 계정·ACL 테스트 계정
  • 승인된 Web Search, Foundry 프로젝트와 모델
  • 별도 구현·승인된 내부 adapter와 테스트 데이터

안전한 운영

  • 테넌트 쓰기·라이브 호출은 별도 승인
  • 토큰·개인정보·내부 URL을 화면·로그에서 제외
  • 네트워크 실패 시 사전 화면 또는 simulation 표시
  • 종료 후 승인된 운영자가 임시 권한·리소스 정리
스피커 노트

비용, 라이선스, 리전, 데이터 경계와 관리자 정책을 사전에 확인합니다. 데모 문서나 dry-run은 실행 승인으로 간주하지 않습니다.

12 / Takeaway

좋은 브리핑은
출처와 한계를 함께 보여줍니다

SEPARATE

근거를 구분

내부 수치·내부 문서·공개 웹의 책임을 섞지 않습니다.

TRACE

원본을 추적

sourceTrace, 문서 링크, URL, 시각과 범위를 보존합니다.

VERIFY

실패도 검증

부분응답과 blocked, simulation/live 차이를 설명합니다.
