# Track3 WebIQ — 발표자 데모 가이드

참석자는 따라 실습하지 않습니다. 발표자가 클라우드의 승인된 환경 또는 준비된
화면을 보여 주며, **공개 웹의 근거를 어떻게 안전하게 확인하고 다음 단계에 넘기는지**
설명합니다. [Track3 실습지](../track3/WORKBOOK.md)가 미션과 완료 기준의 원본입니다.

## 먼저 이해하기

- **FabricIQ**는 내부 정형 수치, **WorkIQ**는 접근 권한(ACL)이 적용된 내부 문서·메일·대화,
  **WebIQ**는 공개 웹의 외부 근거와 URL citation(출처 링크)을 담당합니다.
  **FoundryIQ**는 권위 지식을 제공하고 Foundry Agent Service가 도구를 오케스트레이션하며
  근거를 결합·평가합니다.
- 웹에서 같은 시기에 무언가 일어났다는 사실만으로 내부 문제의 원인을 확정할 수 없습니다.
  가상 상품을 실제 리콜 대상과 같은 제품으로 취급하지 않습니다.
- `dry-run`은 설정·계획 점검, `simulation`은 고정 데이터로 계약을 재현,
  `live`는 승인된 실제 서비스 호출입니다. 이 문서의 Python 검증은 **simulation**이고
  웹 검색, 현재 사실, 사용자 권한 또는 참가자 실습을 증명하지 않습니다.

## 발표 전 준비

1. Track1의 `[TRACK2_WORKIQ_HANDOFF_PACKAGE]`에서 Ontology 식별 정보, 엔터티·관계
   수, 핵심 경로 3개, 매핑 5개 이상, 구현 제한, 검색 키와 의미 경로 로그를 확인합니다.
   Track2는 이 키로 내부 근거를 찾습니다.
2. Track2의 `[TRACK3_WEBIQ_HANDOFF_PACKAGE]`에서 소스별 인덱스 카탈로그, 8개 품질
   점수와 미달 항목, 유효 내부 근거 링크 5개 이상, 우선 이슈 3개, 재현 질의 3개를
   확인합니다. 품질 항목 **8개 중 6개 이상이 각각 75점 이상**, 고정 검색어 5개 중
   4개 이상 성공해야 합니다. 미달하면 담당자에게 보정 요청하고 미검증 상태를 표시합니다.
   상세는 [Track2 실습지](../track2/WORKBOOK.md)입니다.
3. 클라우드 발표 환경에 저장소와 Python 3를 준비하고, 터미널 작업 디렉터리를 저장소
   루트로 엽니다. [source catalog](../track3/data/source_catalog.json)와
   [fixture](../track3/data/web_evidence_fixture.json)를 편집기에서 열어 둡니다.
   Python 검증은 키가 필요 없고 파일을 수정하지 않습니다.
4. **선택 live**: 격리 환경의 Foundry 프로젝트·모델·Foundry Agent Service Web Search,
   권한, 외부 전송·비용 정책을 운영자와 사전 승인받습니다. UI 명칭과 도구 가용성은
   테넌트/버전에 따라 달라질 수 있으므로 사전 리허설합니다.
   불가하면 fixture로 전환하고 live는 미검증으로 남깁니다.
   외부 검색 전송 경계는 [출처 거버넌스](../track3/docs/WebIQ_Introduction_and_Source_Governance.md)를 확인합니다.
5. 화면에 비밀, 실제 사용자 정보, 내부 URL, 미공개 수치를 띄우거나 검색어로 보내지
   않습니다. 웹 페이지의 지시문은 실행할 명령이 아니라 검토 대상 데이터입니다.

## 기존 미션을 발표로 전환

| 원래 미션 | 발표자가 보여 줄 것 | 확인할 결과 |
| --- | --- | --- |
| 1 안전한 검색어 | 내부 질문에서 공개 확인 질문만 분리 | 민감정보 0건, 시간·지역·공식 출처 조건 |
| 2 Web Search 또는 fixture | 승인된 live 검색 또는 아래 fixture 검증 | 실행 모드와 citation을 분명히 표시 |
| 3 출처 품질 | citation 한 건과 6개 평가 항목 비교 | 6개 중 5개 이상 PASS, 한계 기록 |
| 4 Track4 인계 | WebIQ 인계와 Track2 내부 근거 나란히 표시 | Q1~Q3 각각 citation 2개 이상 |

기존 일정은 [통합 계획](../common/docs/Microsoft_IQ_Workshop_Integrated_Plan.md)의
480분 일정과 Track3 35분을 유지합니다. 발표자는 미션을 합쳐 시연할 수 있지만
참가자가 직접 실행했다는 증거로 기록하지 않습니다.

## 화면 1 — 질문을 공개 검색용으로 바꾸기

1. Track2 인계의 공통 Q2를 보여 줍니다: “배송 지연과 반품·불만의 관계는?”
   고객명·주문번호·이메일·내부 URL·미공개 지표·토큰은 제거합니다.
2. catalog의 Q2 `webQuestion`과 `queryTemplate`을 엽니다. 공개 가능한 기간·지역이
   확인된 경우에만 공식 기상/교통 공지를 묻습니다. 지역이 없으면 이를 명시하고
   내부 원인과 직접 일치한다고 가정하지 않습니다. 전송 내용을 발표자가 확인합니다.
3. Q1은 공식 결제 서비스 상태 공지, Q3는 전자제품 **범주**의 공식 안전
   공지나 보안 지침을 묻습니다. 샘플 배송 데이터에 지역이 없으면 직접 원인을 말하지
   않습니다. Q4·Q5 공개 확인 질문은 실습지에 있지만 기본 fixture/자동 검증은 Q1~Q3만
   포함합니다.

> **멘트:** “내부 질문 전체를 웹에 보내는 게 아닙니다. 공개적으로 물어볼 수 있는
> 부분만 따로 떼어냅니다. 웹 출처는 내부 수치 계산을 대신하지 않습니다.”

## 화면 2 — 기본 경로: fixture 검증

저장소 루트의 터미널에서 발표자가 실행합니다.

```bash
python3 track3/data/validate_webiq_sources.py
```

화면에 `scenarios: 3`, `citations: 6`, `result: PASS`가 나타나는지 확인합니다.
편집기에서 fixture의 Q2 두 항목을 펼쳐 `title`, `url`, `domain`, `observedAt`,
`scope`, `factStatus`, `limitations`를 짚습니다. 이 데이터의 `fixture-contract`와
`source-capability`는 **출처를 확인하는 방법의 예시**이지 현재 기상·교통 경보의 증거가
아닙니다. 검증기는 필드·도메인·시각 형식·개수 등을 검사하지만 URL 접속, 최신성,
주장의 사실 여부, 6개 품질 항목의 사람 평가를 증명하지 않습니다.

> **멘트:** “PASS는 샘플 인용의 형식이 맞다는 뜻입니다. 지금 경보가 발생했다는 뜻이
> 아닙니다.”

## 화면 3 — 선택 경로: 승인된 live Web Search

별도 승인이 없으면 이 화면은 실행하지 않고 위 fixture 화면으로 진행합니다.

1. 승인된 Foundry 포털에서 대상 프로젝트와 배포된 모델을 열고 Agent Service 에이전트를
   만들거나 사전 준비한 에이전트를 엽니다. 도구에서 Web Search를 추가·활성화하고
   테스트 화면을 엽니다. 메뉴가 다르거나 도구가 제공되지 않으면 운영자에게 확인하고
   fixture로 전환합니다. WebIQ의 별도 제한 접근 API 사용을 전제하지 않습니다.
2. 공개용으로 검토한 Q1~Q3 질문을 각각 실행합니다. 답변의 citation을 열어 공식
   원문과 기간·지역·범주를 검토하고, 각 질문에 최소 2개를 기록합니다. 제목, 실제 URL,
   도메인, 관찰 시각, 적용 범위, 한계를 보존하고 `factStatus=live-observation`으로
   표시합니다. 가상 상품과 실제 제품은 별개입니다.
3. citation이 없거나 확인 불가하면 설정·권한·검색어를 점검하고 확인 불가로 남깁니다.
   fixture를 live 결과에 끼워 넣지 않습니다. 외부 행동은 사람 승인 전 실행하지 않습니다.

> **멘트:** “이번 화면은 승인된 실제 검색입니다. 링크와 관찰 시각을 확인해야 하며,
> 검색 결과는 내부 문제의 인과관계를 자동으로 증명하지 않습니다.”

## 화면 4 — 품질과 인계

화면에 다음 6가지를 놓고 발표자가 PASS/FAIL과 이유를 기록합니다:
**권위성, 최신성, 관련성, 교차확인, 인용성, 안전성**. 중요한 주장은 독립 출처 2개
이상으로 확인합니다. `scope`는 `direct-match`, `category-level`, `source-capability`
중 실제로 뒷받침되는 수준을 선택합니다. fixture의 두 링크가 같은 사건을 교차 확인하는
것은 아닙니다. 품질 **5/6 이상**을 확인하지 못하면 미통과로 표시하고 보완합니다.

[인계 템플릿](../track3/PREREQUISITES.md)을 열어 발표자가
`[TRACK4_FOUNDRYIQ_HANDOFF_PACKAGE]`에 팀·시각·`executionMode`·Q1~Q3·검색어
기록 참조·citation·품질 결과·불확실성·privacy 점검·사람 승인 필요 여부를 기입합니다.
템플릿의 축약 citation 문자열 외에도 각 citation의 `domain`, `factStatus`, `limitations`를
별도 기록에 보존합니다. Track2 내부 근거 패키지는 WebIQ citation과 **별도로** 함께
넘깁니다. 이 패키지는 발표자가 작성하는 인계물이며 아래 Track4 simulation CLI가
직접 읽어 실행하는 파일은 아닙니다.

> **멘트:** “출처 링크가 있다는 것과 그 출처가 이 질문에 정확히 적용된다는 것은
> 다릅니다. 적용 범위와 모르는 부분도 다음 단계에 전달합니다.”

## 막혔을 때와 종료

| 증상 | 복구 |
| --- | --- |
| Python 또는 파일 없음 | 저장소 루트와 Python 3 설치를 확인하고 경로를 복원한 뒤 검증 재실행 |
| fixture 검증 FAIL | 오류의 시나리오·필드·허용 도메인을 원본 파일과 비교; 임의로 사실을 채우지 말고 담당자에게 보정 요청 |
| live 권한·도구·비용 승인 없음 | 호출하지 않고 fixture로 전환; live 검증 미완료 기록 |
| live citation 부족/출처 품질 미달 | 검색 조건과 공식 원문을 다시 확인; 충족 전 인계 보류 또는 미확인 경고 |
| Track2 게이트 미달 | 내부 근거 보정 요청; fixture 데모는 가능하나 내부 live 검증 성공이라 말하지 않음 |

발표 기록에는 실제 실행 모드, 시각, 검증 결과와 한계만 남깁니다.
