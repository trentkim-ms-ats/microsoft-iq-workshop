# Appendix — FoundryIQ의 WorkIQ 연동 및 M365 인덱스 검색 API 기술 안내

이 문서는 Track3에서 자주 나오는 질문인  
**“Foundry에서 WorkIQ를 연결할 때 제공 커넥터만 써야 하는가?”**,  
**“M365 인덱스 검색 API는 무엇인가?”**에 대한 기술 안내입니다.

---

## 1) Foundry에서 WorkIQ 연결 방식

결론: **제공 커넥터만 가능한 것은 아닙니다.**

실무에서 주로 3가지 방식이 사용됩니다.

1. 제공 커넥터 방식(기본 권장)
   - 장점: 설정이 빠르고 운영 부담이 낮음
   - 장점: 권한/보안(ACL) 처리, 유지보수 측면에서 안정적
   - 단점: 세밀한 커스텀 로직에는 제약이 있을 수 있음

2. Microsoft Graph 기반 커스텀 연동
   - 장점: 검색/필터링/후처리 로직을 업무에 맞게 설계 가능
   - 장점: 특정 도메인 규칙(랭킹/재정렬/요약 파이프라인) 반영 용이
   - 단점: 개발·운영 복잡도 증가, 오류 처리/권한 관리 직접 구현 필요

3. 하이브리드 방식
   - 기본은 제공 커넥터를 사용하고, 특수 요구사항만 커스텀 API로 보완
   - 대부분 조직에서 현실적으로 가장 많이 선택

---

## 2) M365 인덱스 검색 API란?

일반적으로는 **Microsoft Graph Search API**를 의미합니다.

- 엔드포인트(대표): `POST /search/query`
- 대상: SharePoint, OneDrive, Outlook, Teams 등 M365에 색인된 콘텐츠
- 특징: 사용자 권한 기반(Security trimming)으로 결과가 반환됨

즉, 같은 질의라도 호출 주체 권한에 따라 결과가 달라질 수 있습니다.

---

## 3) 기본 요청 구조(개념)

주요 필드:
- `entityTypes`: 검색 대상 유형 (`driveItem`, `message`, `chatMessage`, `event` 등)
- `query.queryString`: 검색 문자열
- `from`, `size`: 페이징
- `fields`: 필요한 필드만 선택 반환(응답 최적화)

예시:

```json
{
  "requests": [
    {
      "entityTypes": ["driveItem", "message"],
      "query": { "queryString": "campaign A refund delay" },
      "from": 0,
      "size": 10
    }
  ]
}
```

## 4) FoundryIQ 시나리오에서의 활용 패턴

권장 흐름:

1. 질문 분해  
   - 예: “캠페인 A 유입 고객의 반품 급증 원인”
2. FabricIQ 조회  
   - 정형 지표(주문/결제/배송/반품) 집계
3. M365 인덱스 검색 API 호출  
   - 관련 문서/메일/채팅의 맥락 근거 수집
4. 결합 추론  
   - 수치 + 맥락 + 출처를 결합해 답변 생성
5. 응답 출력  
   - 요약 + 대응안 + 근거 링크

---

## 5) 구현 시 필수 고려사항

1. 권한/동의
   - Graph 권한 스코프 및 관리자 동의가 필요할 수 있음

2. 보안/프라이버시
   - 샘플/격리 테넌트 사용 권장
   - 불필요한 민감 정보 수집 금지

3. 인덱싱 지연
   - 최신 문서가 즉시 검색되지 않을 수 있으므로 재시도/타임윈도우 전략 필요

4. 품질
   - 중복 문서/버전 문서 처리
   - 근거 링크 유효성 검증
   - 검색 결과 재랭킹 정책(도메인 우선순위) 필요

5. 운영
   - API 제한(스로틀링) 대비
   - 페이징 및 장애 시 아래 fallback 정책 적용
     - 429/5xx: `Retry-After` 우선, 없으면 초기 호출 후 5초→10초→20초 간격 최대 3회 재시도(총 최대 4회 시도)
     - 검색 실패 지속: FabricIQ 수치만 제공하고 `업무 문서 근거 없음` 경고
     - 링크 접근 실패: 해당 근거 제외, 유효 링크가 0건이면 부분응답으로 처리

---

## 6) 의사결정 가이드(언제 어떤 방식?)

- 빠른 PoC/워크숍: **제공 커넥터 우선**
- 규정/정책/정교한 검색 제어 필요: **커스텀 연동**
- 일반 운영 + 일부 특수 로직: **하이브리드**

---

## 7) 요약

- Foundry에서 WorkIQ 연동은 커넥터만이 유일한 방법이 아님
- M365 인덱스 검색 API(주로 Graph Search API)는 핵심 검색 레이어
- 운영 관점에서는 보안·권한·품질·지연·한도까지 함께 설계해야 안정적인 리더십 브리핑 자동화가 가능함

## 8) Track2 → Track3 전환 시 API 점검 (권장)

Track3 시작 직전에 아래 3개만 확인하면 초반 장애를 크게 줄일 수 있습니다.

1. **인덱스 최신성 확인**  
   - Track2 종료 시각 이후 문서가 검색되는지 키워드 1개로 점검
2. **권한 기반 노출 확인**  
   - 같은 질의를 서로 다른 계정으로 호출해 ACL 차이를 확인
3. **근거 링크 유효성 확인**  
   - 상위 결과 5건의 URL이 실제 열리는지 점검

권장 기록 형식:
```text
[WORKIQ_API_HANDOFF_CHECK]
team=<팀명>
freshnessProbe=<pass/fail>
aclProbe=<pass/fail>
linkProbe=<pass/fail>
blockingIssue=<없음 또는 사유>
[/WORKIQ_API_HANDOFF_CHECK]
```
